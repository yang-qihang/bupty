#### 直达键为什么是 `,` 而不是原先定的 `s`

定稿时选的是 `s`，实现时开发者查出一个真实冲突：
`lib/views/assignments.sh:380` 已有 `s|ENTER)` 分支（提交作业）。全局 case 在 `tui_main` 里
**先于** `handle_${TUI_VIEW}_key` 吃到按键，加全局 `s` 会让「作业页按 `s` 提交」永久失效。

把全部 8 个视图的 `handle_*_key` 分支枚举一遍，已被占用的单字符是
`q r s t p f 1 2`（外加 TAB/ESC/BACKSPACE/ENTER/方向键）。**`,` 空闲**，且它是
「设置 / 偏好」的通用约定键（VS Code、JetBrains、macOS 系统设置都是它），比另造一个字母更好认。

**没有去动 `assignments.sh` 的 `s`**——那是别人已有的功能，不该为新增一个键而削它。

（开发者已实测 `ui_read_key` 对 `,` 原样返回 token `,`，字节 `0x2C`，无变形、无吞掉。）

**被否决的方案**（记录以免重复讨论）：

- **混合大小写 `Bupty`**：6 行高放不下。实测渲染出来 `t` 的竖笔戳出顶栏、`y` 的尾巴歪在一边、`p` 与 `P` 完全相同，整体错位。ANSI Shadow 字体本身不含小写设计。
- **实心粗块 + 投影**：投影会从字母内孔（B 的两个腔、P 的腔）透出来，单色下糊成一团，上色后也偏脏。
- **小写 `bupty` 下沉部版本**：6 行里挤不开，`b` 的竖笔只剩一格宽，认不出来。
- **全 8 个页面都加块**：chrome 涨到约 15 行，24 行终端下首页正文只剩 9 行，卡片会掉到最低档。
- **排法①（块居中 + 账号挂在块右侧）**：chrome 只要 7 行，但右侧文字贴着块的腰，视觉上像「挂」上去的。
- **排法③（只做启动画面）**：唯一不碰 chrome 不变量的方案，但平时看不到。

#### 为什么不做 `UI_SEL_BORDER`

配色实验台 `docs/palette-lab.sh` 里有一个产品没有的角色 `sel_border`（选中框），
实验台在预览时会把首页选中卡片的边框从 `UI_ACCENT` 换成它（`docs/palette-lab.sh:515-517`）。
但把它真正接进产品有两个问题：

1. **会改掉已验收的默认观感。** `lib/ui.sh:97` 明写：dark 主题是「用户已认可的默认观感，
   SGR 值与旧实现逐字节一致，不许改动」。首页选中卡片的边框换色会改掉这套观感。
2. **现有 5 套主题没有取值可用。** 实验台只包含 7 套**新**配色，不含
   dark / light / nord / gruvbox / high-contrast。这 5 套的 `sel_border` 得凭空造，
   而它们恰恰是用户已经点过头的。

所以本轮只做「新增 5 套配色」——这是用户要的交付。`sel_border` 是设计侧的额外想法，
不该顺手改掉已验收的东西。**留作用户单独决定的事项。**

（`tests/unit_palette.sh:241` 断言实验台的 `LAB_UI_ROLES` 有 13 个角色，那是**实验台**的契约，
产品不跟进不影响它——实验台可以领先产品。）

## 2. chrome 账（重要）

`docs/ARCHITECTURE.md` 里有一条硬不变量：

> 帧的 chrome 固定 5 行（顶栏 1 + 分隔线 1 + 页脚 3），正文可用行数 = `UI_ROWS - 5`

当前首页的帧：

```
1 行  顶栏
1 行  分隔线
      正文  = UI_ROWS - 5
3 行  页脚（分隔线 + 状态 + 快捷键）
```

改动后首页的帧：

```
1 行  状态行
6 行  BUPTY 大字符块        ← 新增
1 行  分隔线
      正文  = UI_ROWS - 11
3 行  页脚
```

**chrome 从 5 行涨到 11 行，正文少 6 行。** 24 行终端下正文从 19 行降到 13 行：

| 档位 | 条件 | 24 行终端（当前） | 24 行终端（改后） |
|---|---|---|---|
| A（3×2 卡片） | `UI_COLS >= 79 && body >= 17` | ✅ 19 行满足 | ❌ 13 行不满足 |
| B（2×3 小卡） | `UI_COLS >= 40 && body >= 11` | — | ✅ 13 行满足 |
| C（单列列表） | 其余 | — | — |

**这是必须写进架构文档、并同步改 `unit_responsive.sh` / `unit_home.sh` 的真实代价。**
（我在向用户确认方案时把这一项说成了「chrome 5 → 8 行」，那是漏算页脚 3 行的错误数字，此处更正为 11。）

## 3. 影响面（侦察结论）

chrome 的 `-5` **不是集中常量**——8 个视图各自硬编码自己的预算：

| 视图 | 位置 | 常量 |
|---|---|---|
| home | `lib/views/home.sh:30`（分档）、`:245`（档位 C 行窗口） | `UI_ROWS - 5` |
| settings | `lib/views/settings.sh:112` | `UI_ROWS - 5` |
| public | `lib/views/public.sh:29 / :242 / :349 / :419` | `- 6` / `- 7` |
| assignments / exams / grades | `.../assignments.sh:180`、`exams.sh:160`、`grades.sh:216` | `- 8` |
| classrooms | `lib/views/classrooms.sh:232` | `- 9` |
| schedule | `lib/views/schedule.sh:360` | `- 10` |

**但字符块只出现在首页**，所以：

- ✅ **只有 `lib/views/home.sh` 的两处常量需要动**（且只在块启用时）。
- ✅ 其余 7 个页面、7 组常量、以及它们的渲染逻辑**一行不改**。
- ⚠️ `tui_render_header`（`tui.sh:132-200`）必须按 `TUI_VIEW` 分支：首页出 7 行，其余出 1 行。
- ⚠️ `tui_render`（`tui.sh:237-249`）假定「1 顶栏 + 1 分隔线 + 3 页脚」，需要改成读一个统一口径。

做法：引入单一事实来源 `ui_chrome_rows()`，`tui_render_header` 与 `_home_layout` 都调它，
而不是各自写死。这同时满足 `docs/ARCHITECTURE.md:109` 那句「每次调用都要用最新的
`UI_COLS`/`UI_ROWS` 重算，不要缓存」。

## 4. Ambiguous 宽度风险

大字符块用到的 `█ ═ ║ ╔ ╗ ╚ ╝` **全部落在 `lib/core.sh:265-268` 的 `0x2500..0x25FC` 快路径区间**，被归类为
East Asian Ambiguous（class 3），列数取 `BUPTY_AMBIG_W`。项目里已有同一问题的先例：

> `ui_box_init`（`lib/ui.sh:308-331`）：`BUPTY_AMBIG_W == 2` 或非 UTF-8 时，把整组边框字符从
> `┌─│┐` 退回 ASCII `+ - |`。理由：所有布局代码都假定边框字符占 1 列。

字符块必须挂**同一个开关 `BUPTY_AMBIG_W`**（而不是 `ICON_UNICODE_W`——后者只在图标层可用，
非 TTY / 探测失败时是未定义的）。若 Ambiguous 占 2 列：

- 47 列的字面宽度会实际占 94 列；
- 居中位移 `(UI_COLS - 47) / 2` 全部算错；
- 块的右半溢出到下一行，`unit_responsive.sh` 的溢出断言会直接抓到。

宽度一律用 `core_fit_width` / `_core_width` 量，**绝不用 `${#s}`**。

## 5. 降级阶梯

大字符块是**渐进增强**，任一条不满足就整块不显示、顶栏回到今天的样子：

| 条件 | 行为 |
|---|---|
| `BUPTY_AMBIG_W != 1` | 不出块（同 `ui_box_init` 的 ASCII 退化理由） |
| 非 UTF-8（`core_utf8` 为假） | 不出块 |
| `UI_COLS < 47` | 不出块 |
| `UI_ROWS < 22` | 不出块（见下） |
| 以上都满足 | 出块 |

**`UI_ROWS >= 22` 这条门槛的理由**：22 是「首页仍能保住档位 B」的最小行数
（`body = 22 - 11 = 11`，正好等于档位 B 的阈值）。不加这条，一次装饰就会把首页压到档位 C
的单列列表。这条等于在说：**字符块绝不让首页掉到最低档。**

代价是档位 A 的阈值从 `UI_ROWS >= 22` 抬到 `UI_ROWS >= 28`：

| UI_ROWS | 块 | 首页档位 |
|---|---|---|
| 40 | 出 | A（body 29 ≥ 17） |
| 28 | 出 | A（body 17 ≥ 17） |
| 27 | 出 | B（body 16） |
| 24 | 出 | **B**（body 13）← 最常见的终端高度 |
| 22 | 出 | B（body 11） |
| 21 | 不出 | A（body 16 ≥ 17？否 → B） |
| ≤ 21 | 不出 | 与今天完全一致 |

**这张表要原样报给用户**：24 行终端下首页会从「3×2 大卡片」掉到「2×3 小卡片」。

### 强制开关

照 `BUPTY_FORCE_ICONS` 的先例加 `BUPTY_FORCE_BANNER`：

- `BUPTY_FORCE_BANNER=1` → 忽略 `UI_COLS`/`UI_ROWS`/`BUPTY_AMBIG_W` 门槛，强制出块（测试用）。
- `BUPTY_FORCE_BANNER=0` → 强制不出块。
- 未设置 → 按上表判定。

**关键性质**：测试环境（非 TTY、`BUPTY_AMBIG_W` 未探测）下块默认**关闭**，因此
`unit_home.sh` 现有的全部断言**原样通过**。块启用后的行为另开测试覆盖（`tests/unit_banner.sh`）。

（注意：这里说的是 `unit_home.sh` 的**断言**原样通过，不是「整帧逐字节一致」——
后者有一处已知例外，见第 8 节验收标准第 3 条的更正。）

## 6. 已知质量债

### 6.1 三套新主题的 `UI_SEL` 与 `UI_ACCENT` 同索引

`kanagawa`、`latte`、`rosepine` 三套里，`UI_SEL` 直接复用了 `UI_ACCENT` 的索引：

| 主题 | ACCENT | SEL |
|---|---|---|
| kanagawa | 110 | 110 |
| latte | 27 | 27 |
| rosepine | 24 | 24 |

原因：备选色（kanagawa springBlue / latte mauve / rosepine iris）在各自的底色上过不了 WCAG AA 4.5，
开发侧选择退回复用 accent。

**但这是个真实的观感损失，不是纯理论问题。** 首页选中卡片的画法是
（`lib/views/home.sh` 档位 A 约 78 行、档位 B 约 173 行）：

```
选中：bcol = UI_ACCENT（边框）    tcol = UI_SEL（名字）
未选：bcol = UI_BORDER（边框）    tcol = UI_TEXT（名字）
```

两者同色时，**边框与名字合并成同一个色相**——丢的是「两个相互独立的颜色维度」中的一个。
dark 主题里 ACCENT=39 / SEL=81 是刻意拉开的，
`lib/ui.sh:105` 的注释也写明 SEL 的定位是「选中前景·无背景，比 accent 更醒目」。

> **措辞更正**（code review 子 agent 指出，原稿过度渲染了）：
> 本节初稿写的是「选中状态就只剩一条线索、名字的高亮完全消失」，**那是夸大**。实际上——
> 1. `▶` 标记是**独立于配色**的结构线索（档位 A 只有选中卡片带 `▶`；档位 B/C 选中 `▶`、未选 `▸`），配色怎么变它都在；
> 2. 名字**仍然会变色**：这三套的 `UI_TEXT` 分别是 187 / 240 / 60，与各自 accent 的色相明显不同，
>    选中时名字由 `UI_TEXT` 跳到 accent 色相，这一步肉眼可见。
>
> 准确的定性是「**轻度观感损失**」（rosepine 的 60 vs 24 色相最接近，最不明显），
> 而不是「选中态失去辨识」。留此更正以免后人据错误的严重度去改设计。

**为什么自动化测试抓不到**：`tests/unit_palette.sh:413-427` 只断言
`UI_SEL` 索引 ≠ `UI_TEXT` 索引、且 ≠ `UI_MUTED` 索引。SEL == ACCENT 不违反任何断言。

**待定**：是否给这三套重挑 SEL（浅色主题可参考现有 `light` 主题的 ACCENT=26 / SEL=20 的
「同色系加深」做法），或接受现状。留给用户决定。

## 8. 验收标准

任务 B：
1. `UI_COLS=100, UI_ROWS=30` 的首页里，`BUPTY` 块 6 行完整、左右留白差 ≤ 1 列。
2. `UI_ROWS=24` 时首页落到 B 档（2×3 小卡），而不是溢出或截断。
3. 任一降级条件触发时，首页帧与改动前逐字节相同——**唯一例外是页脚那一行快捷键提示**。
   > **更正**：本条初稿写的是无条件「逐字节相同」，**那是不准确的**。页脚提示串
   > （`tui_render_footer`）是全部 8 个页面共用的，而用户要求给它加上 `c 设置`，
   > 所以这是一处**有意的、跨全站的行为变更**。
   >
   > 实测（8 页 × 7 尺寸 = 56 帧逐帧逐行比对）：
   > - **完全相同的帧 40 / 56**；
   > - 有差异的帧 16 / 56——正是宽到能放下完整提示的 `100×30` 与 `80×24` 两个尺寸各 8 页；
   > - **差异行 = 页脚快捷键提示行 16 行；其他行差异 0 行**。
   >
   > 也就是说首页顶栏与大字符块那部分（含块关闭时整条 ` bupty 首页 … ⚙ 设置`）仍然逐字节未变，
   > 变的只有全站共用的那一行提示。
   >
   > **复测（2026-10-14，第二轮配色落地后，主 agent 自测，脚本 `tmp_headcmp.sh`）**：
   > 上面那组 40/16 是在**开发 E 改截断策略之前、且底色铺屏之前**测的，**已过期**，
   > 复测后结论要分两层说，不能只报一个数：
   > - **原始字节 vs HEAD：完全相同 0 / 56。** 每一帧都不同——这不是回归，是配色那一轮的
   >   **既定效果**：`UI_BG` 给每个上色格子加了底色、`UI_RESET` 改成「复位 + 补底色」，
   >   于是每行的转义字节都变了。所以「与改动前逐字节相同」这句话在配色落地后**字面上不再成立**，
   >   它管的对象已经变了。
   > - **归一化后（只抹掉 `\033[48;5;Nm` 这一种变换，其余一律保留）vs HEAD：
   >   完全相同 8 / 56，有差异 48，且 48 处差异 100% 只落在页脚提示行（超出页脚行 = 0）。**
   >   即**降级路径的顶栏 / 正文 / 状态行逐字节未变**，本条验收标准的**实质**仍然成立。
   >
   > 复测口径（写清楚免得下次再对不上）：8 视图 × 7 尺寸（`120×40 100×30 90×28 80×24

## 10. 第二轮：底色铺屏 + 配色选择器（2026-10-14 用户验收反馈）

### 10.0 问题（有实测数字，不是感觉）

用户反馈「这几套配色和现在的黑色背景搭配起来有点过于暗」。量出来是**真的**：

| 主题 | 黑底最低对比度（正文/次要/选中三角色取最小） | 判定 |
|---|---|---|
| light | 1.39 | 不可读 |
| latte | 2.95 | 不可读 |
| rosepine | 2.99 | 不可读 |
| kanagawa | 4.00 | 未达正文线 4.5 |
| dark / nord / gruvbox / high-contrast / mocha / tokyonight | 5.32 – 11.06 | OK |

根因：**产品从头到尾不铺背景**，12 个角色全是前景色，画在用户终端自己的底色上。
而 light / latte / rosepine 是**按白底设计**的（深字压白底），落到黑底就成了深字压黑底。
这是设计前提与实际底色不匹配，调数值修不了。

用户拍板：**主题自带底色、整屏铺；选色器做成列表 + 实时预览；10 套统一处理。**

### 10.1 冻结的接口（两个开发 agent 必须照这个写，不许各改各的）

**角色表 12 → 13**，新增 `UI_BG`：本主题的**背景** SGR，形如 `$(core_sgr "" <idx>)`
（即 `\033[48;5;<idx>m`）。10 套主题**全部**要声明。

**`UI_RESET` 改为「重置 + 立刻恢复底色」**：`UI_RESET="$(core_c_reset)${UI_BG}"`。
这是让现有**几百处** `ui_paint` 调用点自动带上底色的唯一低风险办法——不去改每一个调用点。
`UI_BG` 为空时退化为纯 `\033[0m`（模块加载时、尚未应用主题时的安全默认）。
注意 `UI_RESET` 目前是 ui.sh 加载时赋值一次的常量（`lib/ui.sh:25`），必须改成随主题更新。

**`ui_paint` 新增角色 `bg`** → `${UI_BG}`，供需要显式铺底的调用点用。

**整帧起手带底色**：`tui_render` 必须在 `\033[2J` **之前**先发出 `UI_BG`，
让「擦屏」这个动作本身就带着底色（依赖 BCE；现代终端普遍支持）。

**退出必须干净**：离开备用屏幕前发一次 `\033[0m`，否则用户的 shell 提示符会被染上底色。
`tui.sh` 的 EXIT trap 与 `ui_exit_alt_screen` 两条路径都要覆盖。

**底色取值来源**：`docs/palette-lab.sh`。用它的 `lab_nearest256` 把设计底色 hex 落成 256 索引，
产品值必须与实验台值**逐字节一致**（沿用现有配色护栏的口径）。
`LAB_BG_BASE` 目前只有 7 项（mocha/tokyonight/nord-frost/gruvbox-warm/kanagawa/latte/rosepine），
需补登记 **dark / light / high-contrast** 三项。

> **事后注（2026-10-14）**：上面这句「补登记到 `LAB_BG_BASE`」**就是那个坑的源头**。
> 照字面执行的结果是把 10 项塞进一个只有 7 个名字的平行数组里，长度脱钩、
> 后 3 项永远读不到，还让计数断言变红（见 §10.5 第 2 条）。**修的方向与这句相反**：
> 那 3 项搬进了独立命名的 `LAB_BG_EXISTING`，`LAB_BG_BASE` 回到 7 项并由 `LAB_NAMES` 派生。
> 教训：**「补登记」类指令要写明补进哪个数组、以及那个数组的语义边界**，
> 否则执行者会往最近的那个数组里加。

### 10.2 可以静态验证的不变量（测试必须守住这几条）

### 10.3 选择器

**分工的口径是「按文件切」，不是「按功能切」**：`tui.sh` **整体归开发 A**，
开发 B **只写 `lib/views/settings.sh`**。两人零文件冲突，可真并行。

> 为什么 Esc 需要动 `tui.sh`：`tui_main` 的全局 `case` 里 `ESC|BACKSPACE) tui_back ;;`
> **先于**页面的 `handle_*_key` 命中，所以按现在的结构，Esc 压根到不了设置页，
> 「Esc 取消预览并还原」根本实现不了。解法是加一条**通用**的页面接管钩子（不是设置页专用）：

```bash
# tui.sh 全局 case 里，把 ESC|BACKSPACE 那一支换成：
ESC|BACKSPACE)
  # 页面可选的接管点：handle_<view>_escape 返回 0 = 这次 Esc 已被页面消费（不返回上一页）。
  # 未定义或返回非 0 = 维持原行为。现有 8 个页面都没定义它，行为与改动前逐字节一致。
  if declare -F "handle_${TUI_VIEW}_escape" >/dev/null 2>&1 \
     && "handle_${TUI_VIEW}_escape"; then
    :
  else
    tui_back
  fi
  ;;
```

开发 B 在 `settings.sh` 里定义 `handle_settings_escape`：选择器开着就还原主题并返回 0，
否则返回非 0（交回默认的「返回上一页」）。

- `theme` 行按 `Enter` → 进入选择态（`SETTINGS_PICKER=1`）。
- 选择态下 `render_settings` **整屏接管**，渲染 10 项主题列表：`›` 指向当前高亮项；
  列表带滚动窗口，矮终端下只渲染能放下的那一段（沿用本页既有的滑动窗口口径）。
- `↑↓` 移动 → **立即 `ui_theme_init <候选>`（实时预览，所见即所得），不落盘**。
- `Enter` → `settings_set theme <候选>`，退出选择态，状态栏提示已保存。
- `Esc` → `ui_theme_init <进入选择器时的主题>`（还原），退出选择态，**不落盘**。
- 保持 `←→` 的「循环下一个」快路径不变（现有行为，别削）。
- 已知取舍（如实记录，不藏着）：`q` 与 `Tab` 在 `tui_main` 里是全局键，会先于页面 handler
  被吃掉，所以**选择器打开时按 `q` 仍然会退出程序**。这与全站「q 总是退出」一致，
  本轮接受；若要拦，就得动 `tui.sh` 的全局 case，会破坏并行解耦，故不做。

### 10.3.1 开发 B 交付后，主 agent 复核出的两处待议（已记，留给评审判）

1. **Esc 还原后没有任何反馈。** `handle_settings_escape` 还原主题、关掉选择器就直接 `return 0`，
   不设 `tui_set_status`。用户按 Esc 后界面颜色变回去、但状态栏没说话，可能以为是卡顿。
   对比 Enter 路径是有提示的（「已保存配色方案：X」）。建议补一句「已取消，配色未更改」。
2. **`settings_set` 失败时内存与落盘会不一致。** Enter 路径里实时预览已经把 `UI_THEME`
   切到候选了；若 `settings_set` 失败，本次会话是候选色、磁盘上还是旧值，下次启动会对不上。
   状态栏虽提示了「保存失败」，但没把预览回滚。属边缘情况，但要么回滚要么在注释里写明。

### 10.5 主 agent 复核（第二轮）

上一轮的教训是「只核 diff 形状不算核过」。这一轮把复核方式换了，三条：

1. **真跑**：8 页面 × 10 主题 × 5 尺寸 = 400 帧全渲染，外加选择器交互（开 / 上下 /
   Enter / Esc / 未知键），stderr 去重汇总，要求「一条不剩」。
2. **算结果，不数过程**：写了一个小的终端模拟器（维护 `(字符, 前景, 背景)` 屏幕缓冲，
   按真实语义处理 `\033[2J` 的 BCE / `\033[H` / `\033[J` / `\033[<n>m`），
   把一帧跑成最终像素，然后数「有多少格子掉回了终端自己的底色」。
   这比在字节流里数 `\033[0m` 出现几次硬——它管结果，不管过程怎么写。
3. **变异自检**：模拟器必须能测出漏色，否则它报的 0 没有意义。做法是把每一处
   「复位后补底色」剥成裸复位，看它会不会报警。实测变异帧 2497 格报警 → 灵敏度成立。

#### 主循环内端到端：Esc 撤销是**真驱动 `tui_main`** 验的

在这之前所有复核都是**直接调页面函数**。这一条补上真主循环：只桩掉终端 I/O
（`ui_raw_mode`/`ui_size`/读键），键分发、`tui_main` 的全局 `case`、`handle_settings_escape`、
`ui_theme_init`、`settings_set` 全部走真代码，然后往主循环里喂键。

`UI_THEME_NAMES = (dark light nord gruvbox high-contrast mocha tokyonight kanagawa latte rosepine)`。
喂的键序 `,` DOWN DOWN DOWN ENTER DOWN DOWN ESC ESC q，下表每行是**读该键之前**的状态：

| 读键 | 主题 | 选择器游标 | 原主题 | 视图 | 选择器 |
|---|---|---|---|---|---|
| `,` | dark | 0 | ? | home | 0 |
| ENTER | dark | 0 | dark | settings | **1** |
| DOWN | **light** | 1 | dark | settings | 1 |
| DOWN | **nord** | 2 | dark | settings | 1 |
| **ESC** | **dark** | 2 | dark | settings | **0** |
| ESC | dark | 2 | dark | **home** | 0 |

结论：打开时游标**就停在当前已应用的主题**（dark 的下标是 0）；UP/DOWN 实时预览；
**Esc 还原成原主题并关闭选择器、视图不跳走**；第二次 Esc 才返回上级；`settings_set` 未被调用（落盘仍为 dark）。
四条设计行为全部对上。

#### 三条「前提已破」的断言：诊断与重写口径

测试里有三条断言的前提被这一轮自己的改动打破了。**前提破了 ≠ 产品坏了**，
但也不能因此把允许差异放大到绿色——那等于把断言偷偷删掉。逐条给诊断与重写口径：

**1. `unit_home.sh`「帧内不得出现 `48;5;`」（18 例失败）**
原意：选中卡片曾把带背景的 `UI_HL_FG` 当**纯前景**用，9 列文字区漏出一块游离底色。
